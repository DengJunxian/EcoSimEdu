## 实际浏览器验收

在旧提交的浏览器页面以种子 1962 保存真实仿真作答，限价 96，原预测「不会成交」，政策组每方每件收费 6。把旧记录原样导入独立验收档案，通过新版笔记打开两侧事件 4。每侧均核对买家 B01、卖家 S02、成交价 96、先在簿的 O001 以及原卖单 O003。同一运行 ID 下单独修改成交价或主体的契约测试均拒绝回查。浏览器测试还打开摘要不符的记录，确认解释文字仍然可读。[旧解释夹具](../../../tests/fixtures/progressive-note-8fc8971.json) · [回查测试](../../../tests/e2e/test_domain_notes.py)

在 Chromium 与 WebKit 使用独立持久档案跑完双向拍卖。第一天到第三阶自动暂停在事件 4，关闭浏览器，再以同一档案把页面日期调到次日。首页回到第三阶，保留 96 代币报价、「不会成交」的预测及原游标，事件 5 仍未揭示。从暂停卡回查 O003 的 78 代币卖价，回到成交后推进一步，再完成政策对照。保存后从实验笔记打开解释及两侧原事件。课程全程限制为同源静态 GET。SVB 另在两引擎和 1180、390 像素下保存及回查 D01 的实际到账，核对单笔银行现金增量 -19，并区分该轮首尾账表。[跨日脚本](../../../frontend/tests/continue_browser.py) · [SVB 脚本](../../../frontend/tests/svb_browser.py)

在 320 × 568 的 WebKit 触摸视口发现「下一步」紧随两张订单和剩余核算时被底边截住。把成交价依据与操作按钮提到明细之前。同一触摸尺寸下，Chromium 和 WebKit 均完整显示价证及按钮，并通过触摸推进、保存解释和回查双方来源。[暂停组件](../../../frontend/src/AuctionClassroom.tsx)

- **Codebase Design** 使用原课件、两套原仿真和原库读接口作为数据所有者，标准契约在已有导出与回看入口组装。
- **Analyze Data Quality** 核对粒度、主体 ID、事件顺序、摘要范围、原始来源和缺值口径。用真实成交订单、SVB 实付和历史 SQLite 输入检查适配后的记录。
- **Impeccable** 在原界面系统下核查焦点、暂停反馈、窄屏次序和原事件页面。改动的课堂、笔记、解释及对照组件通过本机检测，返回空数组。
- **Playwright** 使用独立档案实跑跨日重启、双方证据回查和损坏证据状态。原生浏览器内核的学生通路检查覆盖键盘及缩窄视口。
- **两份 Anti-Defensive Writing** 用来源、口径、已通过项与核验范围编写契约和执行记录。

旧笔记的可信回查覆盖 `8fc8971` 的 358 条受支持运行。旧版保存时缺少摘要，更早或未登记版本仅能保留解释文字。本轮使用浏览器校验日期模拟隔日，使用模拟窄屏验证布局和交互。实体手机与原生读屏没有参加本轮测试。
